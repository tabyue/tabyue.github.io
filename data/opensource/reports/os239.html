Alpamayo Recipes 是 NVIDIA 为 Alpamayo 系列机器人基础模型维护的开发者配方库。它的定位不是又一个模型仓库，而是回答一个非常具体的问题：拿到开放权重的机器人基础模型之后，怎么把它调到自己的任务、自己的本体、自己的算力预算上。

本站已收录 Alpamayo 1 Nano（os230）——100 亿参数推理型 VLA，把驾驶轨迹与「因果链」推理配对。alpamayo-recipes 是它的配套工程仓：主仓给权重与架构，recipes 仓给微调、强化学习后训练、量化与部署的可复现脚本。

对正在做真机适配的团队，这类官方维护的 recipes 价值在于把零散的工程经验固化成可 diff、可逐个替换的配置：换一个 LoRA 秩、换一种量化位宽、换一套 RL 后训练目标，都能在同一份骨架上做消融，而不必每次重写训练脚本。

仓库按「配方」组织，大致覆盖四层：

  1. 微调层：在自有示教数据上做监督微调（SFT）的配置与数据格式约定，含 LoRA / 全参两种路径。
  2. RL 后训练层：把真机或仿真回报接进后训练回路的配方，与本期 p315（PrimeSim 用世界模型 rollout 支撑 GRPO）、p312（动作专家梯度路由）讨论的问题直接对应。
  3. 量化与压缩层：FP8 / INT 类量化、KV-Cache 优化与推理加速配置，面向边缘算力（Jetson 类设备）部署。
  4. 部署层：把权重导出成可服务格式、接到机器人运行时的脚本。

结构上它和「框架」类项目不同：不追求抽象出统一 API，而是把每条路径写成可独立运行的最小完整脚本。好处是复现路径短，坏处是跨配方复用时需要自己对齐版本与环境变量。

依赖栈绑定 NVIDIA GPU 生态（CUDA / TensorRT / 对应推理运行时），这是选型时必须先确认的约束。

配方库本身不报告「模型分数」，评估应看工程指标：

  • 复现性：同一 commit、同一数据、同一设备能否得到一致结果。
  • 部署延迟：量化前后在目标边缘设备上的单步推理时间与控制频率。
  • 闭环成功率：不能只看开环动作误差，量化与后训练的影响往往只在闭环里显现。
  • 消融清晰度：每条配方是否只改一个变量，便于归因。

注意

  • 仓库更新频繁，配方与权重版本容易错配，固定 commit 是复现前提。
  • 官方 recipes 默认 NVIDIA 栈，迁到非 NVIDIA 设备需要自行替换推理后端。
  • 量化后务必重跑闭环评测；开环指标对数值偏差不敏感，容易给出过于乐观的结论。
  • 与本站 training-inference-optimization 模块对照读：那里讲量化 / 蒸馏 / 一步生成的原理，这里给可跑的工程实现。

对比 Alpamayo 主仓（os230）：主仓是模型与权重，recipes 是「拿到权重之后怎么办」。两者配套，不是重复收录。

对比通用训练框架（如 LeRobot、Isaac Lab）：通用框架提供数据与仿真抽象，不绑定某一族权重；recipes 绑定 Alpamayo，换来的是更短的路径与官方验证过的默认超参。

对比自己写微调脚本：自己写灵活但难复现、难消融；recipes 把变量显式化，适合做对照实验与团队交接。

对比纯推理优化仓库：多数只做 Serving 加速，不覆盖 SFT 与 RL 后训练；recipes 覆盖从训练到部署的完整链路。
