评测是具身智能最被低估的工程瓶颈

模型侧的创新很容易被看到，但能不能公平、可复现地评出来决定了这些创新是否可信。现实是每家团队都有自己的评测脚本：数据格式不同、任务定义不同、成功判据不同、随机种子不同。结果是论文里的数字无法互相比较，自己团队内的改进也无法稳定归因。

适配矩阵爆炸

设策略数为 $N$、评测环境数为 $M$。若每对组合都要写一份适配代码，成本就是 $O(N \times M)$：

环境 1 环境 2 ... 环境 M
策略 1 适配 适配 适配
策略 2 适配 适配 适配
...
策略 N 适配 适配 适配

每加一个新策略就要写 $M$ 份适配；每加一个新环境就要写 $N$ 份。社区里 $N$ 和 $M$ 都在快速增长，这个矩阵很快就不可维护。

解法：中间表示

把成本降到 $O(N+M)$ 的办法是引入统一的中间表示——策略侧只负责把输出转成标准动作格式，环境侧只负责把观测转成标准观测格式，中间的评测逻辑只写一次：

策略 i ──► 标准动作格式 ──┐
                          ├──► 统一评测流程 ──► 指标
环境 j ──► 标准观测格式 ──┘

inspect-robots 做的就是这件事：定义好两侧的契约，让新增策略或环境的成本变成常数级。

为什么「可视化回放」不是锦上添花

它集成了 Rerun 做轨迹与观测回放。这在评测里是刚需而非加分项——聚合指标只能告诉你「成功率掉了 5 个点」，回放才能告诉你是在哪一步、因为什么掉的。排查失败案例时，缺少回放会让定位成本上升一个数量级。

三层结构

层 职责 新增成本
策略适配层 把任意 LLM/VLA 的输出转成标准动作 每策略 $O(1)$
环境适配层 把任意真机/仿真环境的观测转成标准格式 每环境 $O(1)$
评测核心 任务定义、成功判据、指标聚合、回放 只写一次

标准契约需要定义什么

一份可用的评测契约至少包含：

  1. 观测格式：相机帧（数量、分辨率、时间戳）、本体状态（关节角/速度/力矩）、可能的触觉或力信号；
  2. 动作格式：关节角 / 末端位姿 / 速度 / 力矩中的哪一种，坐标系定义，动作块长度与执行方式；
  3. 任务定义：初始状态分布、目标条件、最大步数；
  4. 成功判据：是二值成功还是部分得分，判据由谁计算（环境内还是外部）；
  5. 随机性控制：随机种子、初始状态采样方式、评测回合数。

为什么第 5 条最常被忽略却最关键

具身评测的方差极大。同一策略换一组初始状态，成功率可能差十几个点。不固定随机种子、不写明回合数，得到的数字不可复现，任何改进都无法归因。这也是很多团队「明明改了但看不出效果」的根源。

真机与仿真的统一难点

真机评测无法精确复位到同一初始状态，因此「固定种子」在真机上退化为「固定初始状态的操作规程」——例如用定位工装保证物体摆放误差在某个范围内。一套好的评测框架必须能表达这种带容差的初始条件，否则真机结果无法与仿真对齐。

接入一个新策略的最小步骤

  1. 实现策略适配器：把模型输出转成标准动作（注意坐标系与量纲）；
  2. 实现环境适配器（若环境已支持则跳过）：把观测转成标准格式，并声明最大步数与成功判据；
  3. 配置评测：回合数、随机种子、是否录制回放；
  4. 运行并产出指标与回放文件。

评测配置示例（概念示意）

eval:
  policy:
    type: vla
    adapter: my_policy_adapter.MyVLA
    checkpoint: ckpt/step-100k
    action_space: joint_position     # 与本体一致的动作格式
  env:
    type: sim                        # sim 或 real
    adapter: my_env_adapter.FrankaTabletop
    max_steps: 200
    success_fn: my_env_adapter.is_success
  protocol:
    episodes: 100                    # 回合数必须写明
    seeds: [0, 1, 2, 3, 4]           # 种子必须固定
    record: true                     # 打开回放录制
  report:
    metrics: [success_rate, steps_to_success, jitter, collision_count]

接入清单（照着做不容易漏）

  • [ ] 动作坐标系与量纲是否与本体一致（最常见 bug）
  • [ ] 动作块执行方式：是执行完整块还是只执行前 $k$ 步
  • [ ] 成功判据由环境计算还是外部计算，是否与论文口径一致
  • [ ] 随机种子与回合数是否已写入配置
  • [ ] 回放是否开启（排查失败案例时不可省）

如何评估一个评测框架

评测框架本身没有准确率，评估它应看它是否让结果变得可复现、可归因：

维度 说明
适配成本 新增策略或环境为 $O(1)$，而非 $O(N)$ 或 $O(M)$
覆盖范围 LLM 与 VLA 两类策略；机械臂与人形两类本体；真机与仿真两类环境
可复现性 随机种子、回合数、初始状态容差可声明
可排查性 集成 Rerun 回放，能定位到具体步与具体原因
许可 MIT，可商用

它解决的成本问题

一个中等规模团队维护自有评测脚本，通常要持续投入在：新策略接入、新环境接入、指标口径对齐、失败案例定位。用统一框架把这四项压到配置级后，评测从「每次都要重写」变成「写完一次长期复用」。

不适用的场景

  • 只需要一次性、临时性的演示（直接写脚本更快）；
  • 需要高度定制化的专有指标且与通用契约冲突（需要先扩展契约）；
  • 追求极致吞吐的大规模分布式评测（需自行扩展并行层）。

一个诚实的边界

统一契约必然带来抽象损耗：某些环境的特有信号（如特殊触觉阵列、专用力传感器）可能无法被标准观测格式完整表达。接入这类环境时要么扩展契约、要么接受信息损失，这个取舍要在接入前想清楚。
