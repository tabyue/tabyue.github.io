核心主张：先把「机器人是谁」告诉 Agent，再让它干活。

多数 LLM Agent 接机器人时失败在第一步：模型不知道自己控制的是什么样的身体——有几个自由度、末端是什么夹爪、传感器装在哪、能承受多大的力。RAI 用 rai_whoami 专门解决这件事：从结构文档、图片与 URDF 自动合成一份embodiment 描述，作为所有 Agent 的共享上下文。

厂商无关的定位：框架不绑定任何机器人型号，能力一律通过 ROS 2 工具暴露，Agent 侧只看到工具接口。这意味着同一套 Agent 逻辑可以迁移到不同平台，只需重跑 rai_whoami 与工具注册。

为什么值得关注 rai_bench：具身 Agent 领域长期缺一个「Agent + 模型 + 工具 + 仿真器」四维一体的评测口径，导致各家的 Agent 效果无法横向比较。rai_bench 把这件事做成了框架内置能力。

1. rai_whoami：本体描述合成

读取结构化文档、图片与 URDF，输出本体描述 $E$，作为 Agent 的系统上下文：

$$ E = \mathrm{Synth}(\mathcal{D}{\text{doc}}, \mathcal{I}, \mathcal{U}{\text{URDF}}) $$

2. rai core：多 Agent 编排

以 ROS 2 工具为动作空间，执行复杂动作、预定义场景与自由形式指令：

$$ a_t = \mathrm{Agent}(o_t, \text{instr}, E) $$

3. 多模态 I/O

文本、语音（ASR/TTS）、视觉（开放集检测）三路统一进 Agent 上下文。

4. rai_bench

对 Agent、模型、工具、仿真器的组合做系统评测，输出可比对的基准结果。

建议的上手顺序

  1. 先跑仿真演示：选与你机器人最接近的一个（Franka / ROSbot XL / 果园拖拉机），先确认工具链路通
  2. 跑 rai_whoami：检查生成的本体描述是否准确——这一步错了，后面所有 Agent 行为都会跑偏
  3. 接语音：先用 rai_asr 单测转写准确率，再接 TTS 闭环
  4. 跑 rai_bench：建立你自己的基线，再逐步换模型/Agent 对比
  5. 上真机：先用低速度限幅跑，确认工具调用不会发出危险指令

本体描述自检

'''
用一组探针问题检查 rai_whoami 生成的本体描述是否可靠
'''
PROBES = [
    '机器人的末端执行器是什么？',
    '一共有多少个可控自由度？',
    '相机装在哪个坐标系、朝向如何？',
    '单臂最大负载是多少？',
]

def audit_embodiment(agent, embodiment, probes=PROBES):
    report = {}
    for q in probes:
        ans = agent.ask(q, context=embodiment)
        report[q] = ans
    return report   # 逐条与 URDF / 手册人工核对

排错要点

  • Agent 频繁调用不存在的关节：rai_whoami 生成的自由度描述与实际 URDF 不一致
  • 语音链路延迟高：ASR 与 TTS 串行执行，改为流式并做首包优化
  • 开放集检测漏检：检查相机内参与 ONNX 运行时版本是否匹配
  • 仿真通真机不通：工具接口一致但话题 QoS 配置不同，检查 reliability/durability
