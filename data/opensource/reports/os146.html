RPent（Recursive Physical Agent）是清华大学于超教授团队联合正行创新、无问芯穹共同发起的新一代具身智能开源项目，目标是构建具身智能持续进化的智能体化基础设施（Agentic Infrastructure）。

一句话：RLinf 负责把模型训出来，RPent 负责让训出来的模型在真实系统里持续跑、持续进化。

三大设计理念

  1. 服务化——实现能力解耦。模型、机器人、技能、记忆、环境各自是独立服务，不绑死在一个进程里
  2. 标准化——实现生态连接。接口标准化后，第三方模型与本体才能接入
  3. 组合化——实现智能重构。能力可以像积木一样重新组合，而不是每次改需求就重写系统

目标是让具身智能系统能像软件一样被构建、扩展和持续进化。

首个核心项目：Harness VLA

Harness VLA 首次把数字智能中广泛应用的 Harness Layer 引入具身智能系统：

  • 保持 VLA 模型冻结
  • 通过 Agentic Planner 对模型调用、任务执行和失败恢复进行统一组织

这个类比很关键：Harness Layer 推动了 Coding Agent 的快速发展——模型能力没变，但外面那层「怎么组织调用、怎么处理失败、怎么管理上下文」的工程设施，决定了能力能不能真正释放出来。RPent 的判断是具身智能正在进入同一个阶段。

一句话总结

模型负责产生能力，而 Harness 负责释放能力。

从「训练一个更强的模型」走向「构建能够持续学习、自主执行、不断进化的智能体系统」，基础设施的重要性正在被重新定义。

为什么 Harness 层要独立

VLA 模型本身是无状态的函数：给观测和指令，输出动作。但真实任务需要的是：

需求 VLA 模型能否提供 Harness 层提供
任务分解 部分 是
多步调用编排 否 是
失败检测与恢复 否 是
执行历史管理 否 是
技能复用 否 是

保持 VLA 冻结是这里的关键设计选择：模型权重不动，所有系统能力在外层叠加。好处是换模型不需要重训系统，坏处是系统能力的上限受模型能力约束。

这与 Coding Agent 的演进路径完全一致——Claude/GPT 的模型权重你改不了，但 Harness 层（工具调用、上下文管理、重试策略）决定了最终效果。

服务化的实际含义

服务化不是微服务化的教条，而是解决具身系统的一个具体困难：模型、机器人、仿真器往往有互斥的依赖。

  • 模型要 PyTorch 2.x + CUDA 12
  • 机器人驱动要 ROS2 Humble，可能要求 Ubuntu 22.04
  • 仿真器可能有自己的渲染依赖

把它们塞进一个进程，依赖冲突会让任何升级都变成灾难。服务化让它们各自独立部署、通过网络通信，是这个现实的直接解。

记忆服务的定位

RPent 把记忆列为与模型、机器人、技能并列的一等服务，而不只是数据库。这对应具身智能的一个真实需求：任务执行历史、失败经验、环境状态变化都需要跨 episode 保留，才能让系统「持续进化」。

概念性最小示例

以下为结构示意，具体 API 以仓库 README 为准：

from rpent import Agent, ModelService, RobotService, MemoryService

# 1. 能力以服务形式声明，而不是写死在进程里
model = ModelService(endpoint='http://localhost:8000')   # VLA 模型服务
robot = RobotService(endpoint='http://localhost:8001')   # 机器人服务
memory = MemoryService(path='./memory')                  # 记忆服务

# 2. Agentic Planner 统一编排
agent = Agent(model=model, robot=robot, memory=memory)

# 3. 执行一个任务：模型冻结，编排与恢复由 Harness 层负责
result = agent.run(
    task='把桌上的杯子放进洗碗机',
    max_retries=3,          # 失败恢复策略在 Harness 层，不需要改模型
)

print(result.success, result.trajectory)

关键实践提醒

不要把失败恢复逻辑写进模型调用里。Harness 架构的核心价值就是失败处理在外层——写进模型调用会让换模型时必须重写恢复逻辑，等于把服务化的收益又丢掉了。

上手顺序建议

  1. 先单独跑通模型服务（一个纯 HTTP 的 VLA 推理端点）
  2. 再接入机器人服务（真机或仿真都行）
  3. 最后加 Agentic Planner 的编排与重试

这个顺序能让你在每一步都验证接口是否正确，避免三层同时调试。

常见坑

  • 服务间延迟：服务化引入了网络通信开销，高频控制回路（1kHz 级）不适合走服务化边界，应保留在本体侧
  • 记忆膨胀：跨 episode 记忆无清理策略会快速增长，上线前先定好保留窗口
  • 依赖版本：RLinf 与 RPent 的依赖栈不同，建议分别用独立环境

性能相关的诚实说明

RPent 是基础设施项目，不是模型。因此不存在「成功率提升 X%」这类可以直接引用的性能数字。它的价值体现在工程维度：

  1. 换模型的成本——服务化后换 VLA 模型不需要重写系统
  2. 失败恢复的可维护性——恢复策略在 Harness 层，可独立迭代
  3. 多本体接入成本——本体抽象为服务后，接入新本体的工作量主要在驱动层

如果你的评估标准是「装上之后成功率涨多少」，这个项目不适合这样衡量；如果你的问题是「我的系统现在换一次模型要大改一遍，怎么解决」，它正是对口的。

关键区别：物理世界约束

数字智能体编排框架可以直接搬到具身场景吗？大部分不行，原因是三个物理约束：

  1. 时间约束：机器人控制有硬实时要求，不能像调 API 一样随时等待
  2. 失败不可逆：数字世界里重试是免费的；物理世界里杯子摔了就摔了
  3. 状态不透明：API 有明确返回值；机器人「抓没抓到」要靠观测推断

RPent 把记忆与失败恢复列为一等服务，正是为了应对第 2、3 点。

什么时候该用

  • ✅ 你有多个模型/本体要接入，且换模型的成本高得离谱
  • ✅ 你的失败恢复逻辑散落在各处，难以维护
  • ✅ 你需要跨 episode 保留执行经验

什么时候不该用

  • ❌ 单模型单本体的简单演示——服务化的开销大于收益
  • ❌ 高频控制回路（1kHz 级）——服务边界的延迟不可接受
  • ❌ 追求开箱即用——这是基础设施，需要自己组装
