双臂操作的两个现实困难

困难一：采集贵。 单臂遥操作一个人还能勉强操作，双臂需要双手协同的时序配合——左手扶住、右手拧，两者的时间关系就是任务本身。用主从臂或 VR 采集，熟练操作员的产出速率和成功率都远低于单臂场景。

困难二：对比难。 各家自己搭的场景、自己定义的初始状态分布、自己写的成功判据，导致论文之间数字不可比。同一个方法在 A 家的场景里 80%、在 B 家 40%，很难判断是方法问题还是环境差异。

数据生成器意味着什么

传统流程是「人采数据 → 训策略 → 上基准评测」，三个环节的数据来源各不相同。RoboTwin 的流程是「基准任务 → 自动生成演示 → 训策略 → 在同一批任务上评测」。

这带来两个直接好处：

  1. 数据规模不再受人力约束：要 1000 条演示，改个参数跑一晚上；
  2. 训练与评测同分布：避免了「训的是 A 场景、测的是 B 场景」这类隐性分布漂移。

专家轨迹从哪来

RoboTwin 的演示不是人采的，而是通过规划与优化在仿真里解出来的。这意味着：

  • 演示动作的最优性取决于求解器质量，而不是操作员水平；
  • 数据里没有人类噪声（犹豫、绕路），这对 BC 是好事（质量高）也可能是坏事（学不到恢复行为）；
  • 可以按需生成任意数量、任意难度的演示。

为什么「成功判据」值得单独设计

双臂任务的成功往往不是单一条件，而是谓词的合取：物体 A 被放到容器 B 内 且 物体 C 未被碰倒 且 双臂未发生碰撞。RoboTwin 把成功判据写成显式的谓词逻辑，好处是：

  1. 可复核：不同论文用同一套判据，数字才可比；
  2. 可细分：能分别统计「抓取失败」「放置失败」「碰撞失败」，定位策略的具体短板。

安装

git clone https://github.com/RoboTwin-Platform/RoboTwin
cd RoboTwin
pip install -r requirements.txt

生成一批演示数据

# 选定任务与本体，生成 N 条专家演示
python -m robotwin.generate \
    --task pick_and_place_dual \
    --embodiment aloha_agilex \
    --num 200 \
    --out data/pick_place_200.hdf5

用生成的数据训练一个策略

from robotwin import load_demo

demo = load_demo('data/pick_place_200.hdf5')
for obs, action in demo:
    loss = policy.update(obs, action)      # 任意 BC / 扩散 / 流策略

在基准上评测

python -m robotwin.evaluate \
    --task pick_and_place_dual \
    --embodiment aloha_agilex \
    --policy checkpoints/my_policy.pt \
    --episodes 100

输出会给出总体成功率以及按失败类型（抓取 / 放置 / 碰撞）的分解。

建议：先用 Clean 设定跑通 pipeline，再切到 Random（随机化初始状态与干扰）设定——后者才是真正区分方法能力的场景，也是论文里通常引用的那个数字。

Clean / Random 双设定

论文里常见的两个数字：

  • Clean：初始状态固定或轻微扰动，考察基本可执行性，多数方法在这里接近饱和；
  • Random：初始位姿、物体外观、干扰物大幅随机化，考察鲁棒性与泛化，这是真正拉开差距的场景。

读论文时的经验法则：只看 Clean 数字没有分辨力，Clean 与 Random 之间的落差才是方法鲁棒性的度量。

它不擅长什么

  • 长程任务规划：RoboTwin 的任务多是单段落的操作，对多阶段规划能力的考察弱于 LIBERO；
  • 开放世界语义：场景与物体集合是预定义的，语义开放度不如 RoboCasa；
  • 真机一致性：作为仿真基准，它不直接回答 sim-to-real 的落差——需要配合 SimplerEnv 类评测一起看。

选型建议

  • 做双臂策略 → 它几乎是当前唯一的主流开源选择；
  • 缺双臂演示数据 → 数据生成器可以直接产出，且 MIT 许可允许商用；
  • 做跨本体迁移 → 它内置多本体支持，省去自己建模的成本；
  • 做长程任务或开放场景语义 → 仍需配合 LIBERO / RoboCasa。
