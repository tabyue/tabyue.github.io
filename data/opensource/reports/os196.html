  2. 故障域共享——语音模块的内存泄漏可能拖垮整张图。

运行时的职责

horus 把自己放在最底层，只管四件事：

   ┌──────────────────────────────────┐
   │  进程 / 节点生命周期管理            │
   ├──────────────────────────────────┤
   │  通信原语（零拷贝优先）             │
   ├──────────────────────────────────┤
   │  时间同步（统一时钟 + 时间戳）      │
   ├──────────────────────────────────┤
   │  资源隔离（CPU 核 / 内存 / 优先级） │
   └──────────────────────────────────┘
                  ▲
                  │
        策略层 / Agent 层 / 中间件在其上

它刻意不提供机器人语义（TF、URDF、Action、参数服务器）——那些属于中间件层的职责。这个切割是理解 horus 的关键：它是运行时，不是 ROS 替代品。

与 Android 的类比

「手机有 Android」这个类比指向的是产业分工：Android 让手机厂商不必各自写进程管理、权限、驱动框架，专注做差异化。horus 想做的是机器人领域的同一件事——把底层共性问题收敛成一个稳定底座，让机器人公司专注在本体与策略上。

这个类比也点出了它的风险：Android 的成功依赖庞大的硬件厂商联盟与兼容性认证体系，机器人领域的本体碎片化程度远高于手机，收敛难度也更大。

四个核心子系统

1. 生命周期管理

节点的启动、健康检查、崩溃重启与优雅退出。与 ROS 2 的差别在于：重启是隔离的——一个节点挂掉不影响其他节点的地址空间（进程级隔离而非线程级）。

2. 通信原语

   发布者 ──► 共享内存（零拷贝）──► 订阅者
                  │
                  └──► 跨进程 / 跨机：序列化传输

同机内优先共享内存零拷贝，跨机走序列化。对高频大带宽数据（点云、图像、关节状态），零拷贝带来的延迟与 CPU 节省是数量级的。

3. 时间同步

统一时钟源 + 每帧时间戳。这是多传感器融合的地基——相机、IMU、力传感器各自有时钟漂移，没有统一时间基准，后续的时序对齐无从谈起。

4. 资源隔离

   CPU 核绑定      ──►  运控独占核，不被其他任务抢占
   内存配额        ──►  单个节点泄漏不影响全局
   调度优先级      ──►  实时任务优先于最佳-effort 任务

为什么 Rust 在这里是合理选择

需求 Rust 的对应特性
无 GC 停顿 所有权 + 无运行时 GC
内存安全 借用检查器消除数据竞争
零成本抽象 泛型与 trait 在编译期单态化
系统级控制 可直接操作内存布局与系统调用

实时系统最怕的是不可预测的停顿。GC 语言（Java / Go / C#）在这个场景先天不利；C/C++ 性能达标但内存安全靠人。Rust 的取舍正好落在中间。

定义两个节点并通信

use horus::prelude::*;

#[horus::node]
async fn camera_driver(pub_img: Publisher<Image>) -> Result<()> {
    let cam = Camera::open(0)?;
    loop {
        let frame = cam.grab()?;
        pub_img.send(frame).await?;      // 同机零拷贝
    }
}

#[horus::node]
async fn policy(sub_img: Subscriber<Image>, pub_cmd: Publisher<JointCmd>) -> Result<()> {
    while let Some(img) = sub_img.recv().await {
        let cmd = infer(&img)?;
        pub_cmd.send(cmd).await?;
    }
    Ok(())
}

为运控节点做资源隔离

# node.toml
[node.controller]
binary = "target/release/controller"
cores  = [4, 5]          # 独占 CPU 核
priority = "realtime"    # 实时调度优先级
memory_limit = "512MB"   # 内存配额，防泄漏扩散
restart = "on-failure"

horus run --config node.toml

与既有 ROS 2 资产对接

horus bridge --ros2             # 启动 ROS 2 兼容桥

桥接模式下，horus 节点可以与 ROS 2 节点互通 topic / service，便于渐进式迁移——先迁运控这类对抖动敏感的模块，其余留在 ROS 2。

定位决定了对性能的表述方式

horus 的口号是「Fastest Robotics Runtime System」，但「快」在这里的正确度量不是吞吐，而是抖动（jitter）。对运行时而言，关键指标是：

指标 含义 为什么重要
周期抖动 实际周期与标称周期的偏差 运控抖动直接决定控制质量
尾延迟（p99 / p999） 极端情况下的延迟 偶发卡顿比平均延迟更致命
CPU 占用 通信与同步的开销 省下的算力可给策略推理
故障隔离度 单节点故障的影响范围 决定系统可用性

读这类项目的数据时要看 p999 而不是均值——平均延迟好看但偶尔抖一下，对 1 kHz 运控就是灾难。

Rust 带来的可预期收益

  • 无 GC 停顿：消除了一整类不可预测的延迟尖峰；
  • 零拷贝通信：大带宽数据（图像 / 点云）避免多次内存复制；
  • 编译期内存安全：数据竞争在编译期被拦截，运行时崩溃概率下降。

三层不要混着选

项目 层 语言 何时选它
horus 运行时 Rust 瓶颈是抖动 / 隔离 / 资源控制
ROS 2 中间件 C++ / Python 瓶颈是生态 / 复用 / 仿真对接
RAI / robonix Agent 框架 Python / Rust 瓶颈是长程任务 / 自主性

与 ROS 2 的关系：不是替代，是可叠加

horus 提供 ROS / ROS 2 兼容桥，意味着可以渐进式迁移：

   阶段一：全部在 ROS 2
   阶段二：运控 / 伺服 迁到 horus，其余留在 ROS 2（走桥接）
   阶段三：按需迁移更多对延迟敏感的模块

这个渐进路径很重要——把整套机器人软件栈一次性换掉在真实团队里几乎不可能，能局部替换才有落地机会。

选型建议

  • 你的运控在 1 kHz 且对抖动敏感 → 值得评估；
  • 你的主要痛点是算法包不够、仿真对接麻烦 → 先留在 ROS 2；
  • 你在做多本体产品线（人形 + 无人机 + AMR）→ topics 显示它覆盖多形态，可统一底座；
  • 团队没有 Rust 能力 → 学习成本要先算进去。
