大多数具身智能体停在了哪一步

一个典型的具身智能体循环长这样：

感知 → 规划 → 执行 → （结束）

问题出在括号里。执行完之后：

  • 没人验证：系统默认「发出动作 = 任务完成」；
  • 没有学习：这次成功或失败的经验不进入任何可复用的地方。

结果是系统在开环运行：每一次任务都是从零开始，同一个坑可以掉一百次。

OpenETA 补上的两段

感知 → 动作 → 验证 → 学习 ──┐
  ↑                          │
  └──────────────────────────┘
  • 验证（verification）：执行之后独立判断「到底做没做成」，而不是把执行器的返回当作真值；
  • 学习（learning）：把验证结果回灌进后续能力——可以是记忆更新、技能库修订，也可以是策略微调的数据来源。

这两段加起来，才构成一个持续的物理世界闭环。

四段的职责划分

段 输入 输出 常见实现
感知 多模态观测 状态/场景表示 VLM、3D 重建、状态估计
动作 表示 + 任务 可执行动作序列 VLA、技能库、MPC
验证 执行前后观测 成功/失败 + 失败类型 状态比对、VLM 判定、程序化检查
学习 验证结果 + 轨迹 更新的记忆/技能/策略 经验库、技能修订、微调数据

为什么「验证」必须独立

一个反直觉但重要的设计原则：不要让执行器自己报告成功。

机械臂返回「trajectory executed」只说明轨迹发完了，不说明杯子被拿起来了。把这类返回当作成功信号，会让整个闭环建立在错误标签上——后面的学习越努力，错得越系统。

独立的验证环节通常需要：

  • 程序化检查（最可靠）：目标状态是否达成，用可计算的谓词判定；
  • 视觉判定（次可靠）：用 VLM 判断前后帧的语义差；
  • 混合：程序化为主，视觉为辅，冲突时报警。

搭一个最小闭环

即使不用 OpenETA，下面这个骨架也值得照着实现一遍：

def run_episode(task, max_steps=30):
    obs = perceive()
    for step in range(max_steps):
        plan  = decide(obs, task)
        exec_actions(plan)
        obs   = perceive()
        ok    = verify(obs, task)      # 独立验证
        learn(plan, obs, ok)           # 回灌
        if ok:
            return SUCCESS
    return FAIL

检查清单

□ verify 是否独立于执行器返回值
□ 失败是否被分类（不是只有 True/False）
□ learn 的产物是否可被后续 episode 检索到
□ 同一失败模式第二次出现时，行为是否不同

最后一条是唯一真正检验闭环是否成立的测试。

成熟度判断

创建于 2026 年 7 月，星标 209，属于早期但方向明确的框架。价值主要在于它把「验证 + 学习」显式列为架构的一等公民，而不是散落在代码里的零散逻辑。

适用边界

适合：

  • 需要长期运行、希望能力随时间提升的机器人系统；
  • 研究具身自改进 / 持续学习的团队；
  • 已有 VLA 或 WAM 底座、想在其上搭组织层的项目。

不适合：

  • 一次性 demo；
  • 没有独立验证手段的场景（如无法判定成败的开放任务）；
  • 对延迟极敏感的硬实时控制回路。
