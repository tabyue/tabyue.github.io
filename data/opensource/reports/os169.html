核心问题：Computer Use 的能力，有多少能平移到 Robot Use？

过去两年通用智能体在数字世界进展神速——写代码、操作 GUI、调用 API。一个自然的推论是：把工具换成机器人，同样的能力就能迁移到物理世界。RobotWorld 的价值在于它不假设这个推论成立，而是把它做成了可测量的题目。

基准设计的两个关键决定：

第一，用可执行的成功判定，而不是让模型自评。 具身评测里最容易被高估的就是「模型说自己成功了」。RobotWorld 由预定义条件判定，且给出显式的交互预算——在预算内完成才算成功。这等价于给「效率」也计了分。

第二，同时分析执行轨迹，而不只看最终成功率。 这是本基准最有价值的部分。只看成功率，你只知道「失败了」；看轨迹，你能知道「失败在哪一环」。论文因此才能得出那个关键结论：智能体具备感知与控制所需的单点能力（写分割程序、估相机参数、建动力学近似），但不能稳定地把它们组合成成功行为。

四条具体失效模式：到达指令位姿却丢失任务相关物体状态；无法纠正无效动作；恢复太晚；把未完成的任务误判为完成。这四条都不是「能力缺失」，而是「闭环缺失」——恰恰是当前通用智能体在物理世界最薄弱的地方。

模型侧的有趣差异：Astra 在空间目标与受约束接触目标上更强，Opus 5.5 在连续平衡与限时交互目标上更强。这说明不同模型的物理世界能力剖面并不同构，选型时不能只看通用榜单。

交互协议

$$ a_t = \text{Agent}(o_t, s_t, \text{feedback}_{<t}), \qquad \sum_t \mathbb{1}[\text{step}_t] \le B $$

智能体通过工具接口获取图像 $o_t$ 与机器人状态 $s_t$，发出动作 $a_t$；总步数受预算 $B$ 约束。

成功判定

$$ \text{success} = \mathbb{1}\big[ \phi_{\text{task}}(\text{world state}) = \text{true} \big] \quad \text{且} \quad \text{steps} \le B $$

由可执行判定函数给出，不依赖模型自报。

验证顺序

  1. 先跑一个单领域子集（建议从操作开始），确认工具接口的观测/动作格式
  2. 用一个强模型跑全 84 项，建立基线成功率与分领域剖面
  3. 导出执行轨迹，按四类失效模式分桶统计——这一步比看总成功率有用得多
  4. 对比不同模型：观察是否存在「A 模型在某类目标强、B 模型在另一类强」的分化
  5. 若做方法研究，优先针对「恢复太晚」与「误判完成」这两类——它们是纯闭环问题，不涉及感知能力

BUCKETS = ['lost_object_state', 'no_correction', 'late_recovery', 'false_completion']

def bucketize(traj):
    if traj.reached_pose and not traj.obj_state_tracked:
        return 'lost_object_state'
    if traj.ineffective_action_count > 3 and not traj.corrected:
        return 'no_correction'
    if traj.recovery_step is not None and traj.recovery_step > 0.8 * traj.budget:
        return 'late_recovery'
    if traj.reported_done and not traj.verified_done:
        return 'false_completion'
    return None

排错要点

  • 成功率全部为零：工具接口的动作空间与模型输出格式不匹配，先跑一个手工脚本验证接口
  • 预算永远不够：先放宽预算跑一遍确认任务可解，再收紧到标准值
  • 轨迹日志缺关键字段：需要显式记录「是否自报完成」与「是否验证完成」，否则分桶做不了
