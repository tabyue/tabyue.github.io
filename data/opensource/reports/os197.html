具身工程里最贵的隐性成本

一个典型的具身算法团队，真机侧通常长这样：

   采数据：  自己写的遥操作脚本 + 自己的数据格式
   训模型：  另一套数据加载器（因为格式对不上，又写了一个转换脚本）
   部署：    第三种接口（因为部署要实时，重写了一套）
   评测：    第四种脚本（因为要统计成功率，又写一遍）

四套代码的接口约定各不相同，于是：

  • 换个本体 → 四套全改；
  • 换个策略 → 部署与评测部分改；
  • 数据格式升级 → 训练与采集部分改，还要写迁移脚本。

真正的代价不是写代码的时间，而是每次改动都要重新对齐一遍四套代码之间的隐式约定。

关键点：策略与本体解耦。策略只面对统一接口，本体差异被封在适配层里。这意味着同一个策略换本体时只改配置，不改代码。

为什么「评测」也要统一

评测常被当成「跑完看个数」，但实际上它是最容易失真的环节：

  • 初始状态怎么摆？（人工随手摆 → 每次分布不同）
  • 成功怎么判？（人眼看 → 主观且不可复现）
  • 失败怎么归？（只看总体成功率 → 不知道该改哪）

把评测纳入同一框架，才能把初始状态分布、成功判据、失败归因都写进配置，让两次实验之间真正可比。

观测契约

不同本体的传感器配置差异很大，统一做法是定义一个标准观测字典：

obs = {
    'rgb':   {'wrist': ..., 'front': ...},   # 相机（可选多路）
    'joint': {'pos': ..., 'vel': ...},       # 关节状态
    'eef':   {'pose': ..., 'wrench': ...},   # 末端位姿与力/力矩
}

缺失的字段允许为 None，策略侧按需取用。这样新增本体只需实现一个「产出这个字典」的适配器。

频率控制的必要性

策略推理频率（10—50 Hz）与机器人控制频率（常为 100—1000 Hz）不一致，中间必须做插值与安全限幅。这一层如果没有框架统一处理，每个策略各写一遍，很容易出现：

  • 动作跳变 → 触发机器人报警甚至危险运动；
  • 时序错位 → 观测与动作不对应，训练时学不到东西。

数据闭环

   遥操作采集 ──► 统一格式落盘 ──► 训练 ──► 部署
        ▲                                    │
        └────────── 评测失败样本 ◄────────────┘

闭环的意义：评测中失败的回合可以直接回流成训练数据（特别是失败前几帧），形成针对性的数据补充。这是「部署—评测—采集」三合一真正的价值——不是省了三份代码，而是让闭环跑得起来。

安装

git clone https://github.com/Noietch/EVA-CLIENT
cd EVA-CLIENT
pip install -r requirements.txt

连接本体并跑一个策略

from eva import Robot, Policy

robot = Robot.from_config('configs/piper.yaml')     # 本体：一行配置切换
policy = Policy.load('checkpoints/my_vla.pt')       # 任意 VLA / WAM / RL 策略

for ep in range(10):
    obs = robot.reset()
    for t in range(robot.max_steps):
        action = policy.act(obs)                    # 统一观测契约
        obs = robot.step(action)                    # 内部做插值与安全限幅
        if obs['done']:
            break
    print('episode', ep, 'success:', obs['success'])

采集遥操作数据

python -m eva.collect \
    --robot configs/franka.yaml \
    --teleop spacemouse \
    --task pick_and_place \
    --episodes 100 \
    --out data/franka_pick_100

落盘的是统一格式，训练侧直接用同一个加载器读取，不再需要转换脚本。

跑标准化评测

python -m eva.evaluate \
    --robot configs/ur5e.yaml \
    --policy checkpoints/my_vla.pt \
    --task_cfg tasks/pick_and_place.yaml \
    --episodes 50 \
    --report out/report.json

task_cfg 里写死初始状态分布与成功判据，保证两次评测可比；报告给出成功率与失败类型分解。

实践建议：先用一个本体 + 一个策略跑通「采集 → 训练 → 部署 → 评测」整条链路，再扩展本体。中途换本体时，只应改动 configs/*.yaml，不应改动任何策略代码。

什么时候该用它

  • 你有真机且需要经常换策略/换本体 → 收益最大；
  • 你的团队只有仿真 → 直接用仿真基准即可，它价值有限；
  • 你在做人形全身控制 → 本体覆盖可能不满足，先确认适配层；
  • 你需要硬实时伺服 → 它工作在策略层，底层运控另需方案。
