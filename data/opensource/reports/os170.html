Coding Agent 是具身操作的第四条范式

理解 EmbodiedEvo 的位置，先要看清四条路线的分工：

范式 谁生成动作 如何根据反馈调整
VLA 学到的策略直接输出动作序列 策略内部（不可解释）
Agent + VLA Agent 规划调度，VLA 出具体动作 双层，责任边界模糊
单轮 LLM/VLM 一次输出结构化动作描述，适配器转换执行 无闭环
Coding Agent Agent 自主编写可执行程序 读执行反馈 → 改代码 → 继续执行

EmbodiedEvo 属于最后一种。它的优势不在单步动作质量，而在长程任务的可分解性与经验的可继承性：一个 30 步的任务在 VLA 里是一个 30 步的动作序列（错了只能重来），在代码里是 5 个可单独调试的函数。

自进化闭环

$$\mathcal{L}^{(k+1)} = \text{Refine}\big(\mathcal{L}^{(k)},\ \text{Feedback}(\text{exec}(\mathcal{L}^{(k)}))\big)$$

其中 $\mathcal{L}$ 是代码库而非策略权重。因为代码是离散、可读、可版本管理的，这个迭代可以被审查、被回滚、被部分替换——这是神经网络权重不具备的性质。

为什么需要「分段提交」

如果每次都提交完整程序，Agent 只能做全局重写，改对的地方也可能被改坏。分段提交 + 回合内状态保留（仿真状态、变量、函数持续存在）让 Agent 能：

  1. 先跑通前 3 步，确认抓取姿态可靠
  2. 保留这 3 步的变量与函数，只追加后续逻辑
  3. 某一步失败时只回滚到该步，而非从头再来

这就是「把一次物理交互变成可复用经验」的机制基础。

控制接口层（四个原语）

"""
EmbodiedEvo 风格的最小控制循环。
注意 docstring 用三引号，与外层字符串定界符区分。
"""
def run_episode(agent, env, max_steps=30):
    instruction = env.get_instruction()
    code_workspace = Workspace()

    for t in range(max_steps):
        # get_observation 不推进仿真，可以安全地多次调用做检查
        obs = env.get_observation()
        patch = agent.write_or_patch(code_workspace, instruction, obs)
        code_workspace.apply(patch)          # 分段提交，变量与函数保留

        action = code_workspace.next_action()
        obs, done, terminated = env.step(action)

        if done or terminated:
            break
    return code_workspace

分层结构

层 职责 是否可学习
Agent（大模型） 写代码、读反馈、决定下一步 否（冻结底座）
代码工作区 承载技能函数与检查条件 是（自进化产物）
适配器 把代码输出转成机器人指令 否
底层控制器 逆运动学 + 动作插值 否

注意分工：底层控制器不做决策，只执行关节/末端位姿目标与夹爪指令。所有「怎么抓」「什么时候继续」的判断都在 Agent 写的代码里。这个边界保证了评测测的是 Agent 的推理能力，而不是底层控制器的质量。

不提供高级技能原语是有意为之

如果接口直接给 grasp(object)，评测就变成了「会不会调用 API」，而不是「能不能从视觉观察里构造出可靠的抓取」。EmbodiedEvo 明确不提供 grasp，Agent 必须自己把 get_observation() 的图像变成接近、对齐、闭合的动作序列。

最小验证流程

  1. 先只跑 get_instruction() + get_observation()，确认能拿到图像与机器人状态，且确认 get_observation() 不会推进仿真（这一步错了后面全乱）
  2. 让 Agent 写一个最简单的两段式程序：接近目标 → 闭合夹爪。只看这两步能否稳定成功
  3. 加上反馈循环：抓取失败后让 Agent 重新观察并修正姿态，记录每次 patch 的 diff
  4. 逐步加长任务，观察「已验证函数」是否被后续任务复用（这是自进化是否真的在发生的判据）
  5. 最后再上 RoboDojo-sim 跑完整评测

排错要点

  • Agent 反复全局重写：分段提交没生效，检查工作区的状态保留是否跨 step 持续
  • 任务进度停在半路：多数是 Agent 没能从图像判断「当前步骤是否成功」，应强化检查条件而非加大模型
  • 仿真里过、真机不过：底层控制器的逆运动学与动作插值存在理想化假设，需加入执行误差容限
  • 代码库膨胀但不复用：缺少「把已验证片段整理成带参数函数」的固化步骤，应显式加一个整理阶段

关键诊断发现

团队分析 Astra 在 RoboDojo-sim 的执行轨迹：在井字棋任务中，模型知道要抓，却还没掌握可靠的抓法。这揭示了通用大模型进入物理世界时的典型断层——语义层面的「知道做什么」与物理层面的「做得稳」是两种能力，后者需要可积累的执行经验，而这正是代码库能承载的东西。

读表要点：EmbodiedEvo 与 RoboRSI 同属「代码即策略 + 自进化」，但着力点不同——RoboRSI 解决归因（哪个技能分支该改），EmbodiedEvo 解决接口与闭环（怎么用最少原语支持长程交互与经验沉淀）。两者互补：把 RoboRSI 的三层契约接进 EmbodiedEvo 的工作区，理论上能同时拿到精确归因与长程调试。

与前一代的差别：Code-as-Policies 时代模型只生成一次代码，错了就废；EmbodiedEvo 的核心增量是持续交互中的代码演化——这是从「生成」到「演化」的跨越。
