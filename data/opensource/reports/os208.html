rosclaw 定位为具身 Agent 的 Physical AI 运行时，不是又一个机器人中间件。

ROS 2 缺什么

ROS 2 解决得很好的是：节点通信（DDS）、服务/动作接口、实时调度、设备驱动抽象。它不解决：

  • 一个由 LLM 提出的动作，该不该执行（治理）；
  • 一次执行产生的轨迹，能不能被后续复用（经验验证）；
  • 机器人在长期运行中积累的空间与物体知识，怎么组织（物理记忆）；
  • 技能库怎么随经验增长而更新，且不破坏已有能力（技能进化）。

rosclaw 声称要补的就是这四块。

四个模块的职责

模块 职责 对应痛点
Governed action 动作执行前的策略/审批层 Agent 提出危险动作无人拦
Verified experience 经验入库前的校验 垃圾轨迹污染训练集
Physical memory 空间与物体信息的持久组织 每次任务都从零认识环境
Skill evolution 技能版本化与迭代 改一个技能破坏其他技能

适用边界

  • 适合：已经能跑通 Agent → 机器人链路，现在要处理长期运行与治理问题的团队；
  • 不适合：还在解决「怎么让机器人动起来」的早期项目——先用 ROS 2 或 robot-control-stack 把链路跑通。

为什么要「受治理的动作」

Agent 提出的动作与规则系统提出的动作有本质区别：前者是概率性的，可能提出从未见过的动作序列。因此执行前需要一道检查层，典型组成：

  1. 安全边界检查：关节限位、速度上限、碰撞预测；
  2. 权限检查：这个动作需要什么级别的授权，当前操作者有没有；
  3. 可回滚性检查：如果这一步做错了，能不能退回来。

这一层是 rosclaw 与纯 ROS 2 方案最主要的区别。

物理记忆与 RAG 的关系

Physical memory 本质上是具身版的记忆系统：不只是文字记录，而是带有空间坐标、物体身份、时间戳的结构化记忆。它与 Embodied-RAG 的思路一致——检索的对象是「机器人去过哪、见过什么、做过什么」，而不是文档片段。

最小运行示例

from rosclaw import Runtime

rt = Runtime(config="configs/minimal.yaml")

# 1) 注册一个受治理的动作
@rt.action(requires_approval=True)
def move_to(x, y, theta):
    return rt.ros.nav2_goal(x, y, theta)

# 2) Agent 提出动作，运行时先过治理层
result = rt.invoke(move_to, x=1.0, y=2.0, theta=0.0)

# 3) 经验入库（带校验）
rt.experience.record(result, verify=True)

# 4) 查询物理记忆
mem = rt.memory.query("厨房台面上有哪些物体")

落地建议

  • 先只开治理层：把动作审批接上是收益最直接、风险最低的一步；
  • 经验库要有准入标准：不加校验地全量入库，等价于把噪声写进训练集；
  • 技能版本化要配回归测试：没有回归测试的「技能进化」等于随机破坏。

风险提示

「受治理的动作」这类机制的价值完全取决于治理规则写得对不对。一个只做权限检查、不做碰撞与安全边界检查的治理层，实际上提供的保护非常有限。采用时应逐条核对它到底检查了什么，而不是只看有没有这个模块。
