运行时仓库解决什么问题

LeRobot Humanoid Runtime 是 Hugging Face 开源双足人形平台的 运行时仓库——把训练好的策略部署到真机的必经环节。

它存在的理由很实际：「仿真里能走」到「真机上能走」之间，隔着一整层琐碎但致命的工程细节。这些细节在论文里通常不写，却是每个做真机的人必须踩一遍的坑。

具体来说：

  • 关节零点标定错了 → 机器人站的姿态是歪的，走两步就倒
  • IMU 没校准 → 姿态估计有偏，平衡控制器基于错误信息做决策
  • 关节运动方向搞反 → 一上电就抽搐，可能损坏电机
  • 仿真控制器与真机控制器接口不一致 → sim2real 时要重写一遍控制代码

Runtime 仓库把这四件事都做成了标准工具。

核心组件

MuJoCo 仿真控制器

与真机控制器 共用接口。这一点是设计上的关键选择：如果仿真和真机各有一套 API，那么每次算法改动都要改两遍，且两者行为可能不一致。统一接口后，同一份策略代码可以直接在两种后端上跑。

真机控制器（CAN + MIT 协议）

基于 CAN 总线 + MIT 协议，内置安全机制。

MIT 协议是 MIT Mini-Cheetah 项目推广的一种电机控制协议，其特点是可以在单个 CAN 帧里同时下发位置、速度、前馈力矩与位置/速度增益：

$$\tau = k_p(\theta_{des} - \theta) + k_d(\dot\theta_{des} - \dot\theta) + \tau_{ff}$$

这个式子看起来简单，但它的工程价值在于 阻抗控制可以在电机侧闭环完成，主控只需下发期望轨迹与增益，不必以 1 kHz 的频率逐帧算力矩。这对主控算力有限的边缘平台特别重要。

内置的安全机制通常包括：位置越限保护、速度越限保护、力矩限幅、通信超时处理（超时后电机进入阻尼模式而非保持最后指令）。

策略推理运行器（ONNX / Torch 双后端）

支持 ONNX Runtime 与 PyTorch 两种推理后端。

为什么需要两个？训练时用 PyTorch 方便调试；部署时 ONNX Runtime 通常更快、依赖更少、更容易在算力受限的主控上跑。双后端意味着 同一个策略文件可以在两种模式下加载，不必为部署单独做模型转换流程。

IMU 集成模块

双足行走是典型的 倒立摆 问题，姿态反馈的精度直接决定能不能站稳。IMU 模块负责：

  • 原始数据读取与时间戳同步
  • 静态偏置标定
  • 与关节编码器数据的融合时序对齐

时序对齐 这一项常被忽略：IMU 通常跑在几百 Hz，关节编码器在 1 kHz，相机在 30 Hz。如果不做时间戳对齐，状态估计器会把不同时刻的数据当作同一时刻，引入系统性误差。

LeRobot 集成控制器

接入 LeRobot 生态，可直接复用其数据集格式、训练流程与可视化工具。

MIT 协议的力矩分解

MIT 协议下的电机侧控制律为：

$$\tau_{cmd} = k_p(\theta_{des}-\theta) + k_d(\dot\theta_{des}-\dot\theta) + \tau_{ff}$$

三项各有分工：

  • $k_p$ 项——位置跟踪，决定刚度。$k_p$ 太大会震荡，太小会瘫软
  • $k_d$ 项——速度阻尼，决定阻尼比。这一项对抑制震荡至关重要
  • $\tau_{ff}$ 项——前馈力矩。重力补偿、惯性力矩都可以放这里，好处是不依赖反馈误差就能输出正确的静态力矩

前馈这一项是实践中最容易被忽略、效果也最显著的一项。没有重力补偿时，控制器必须依靠位置误差来产生支撑力矩，结果是机器人「站得低」——稳态误差始终存在。加上重力前馈后，同样的 $k_p$ 可以让机器人站得更直。

统一接口的设计价值

设控制器接口抽象为两个方法：

class ControllerBackend:
    def get_state(self) -> RobotState: ...
    def send_command(self, cmd: JointCommand) -> None: ...

仿真后端与真机后端各自实现，上层策略只见接口。带来的直接收益：

  1. 同一份策略代码跑仿真与真机，消除「两套代码行为不一致」的问题
  2. 可以在仿真里回放真机日志——把真机采集的状态序列喂给仿真后端，验证仿真保真度
  3. 切换成本低——训练在云上 GPU 跑仿真，部署到本体时只换 backend

第 2 点是 sim2real 调试的关键技巧：如果仿真回放真机轨迹时出现明显偏离，说明仿真器的动力学参数（质量、惯量、摩擦）与真机不符，应优先修正模型而非调策略。

时序同步的处理

不同传感器频率不一致是常态。设：

  • 关节编码器：$f_j \approx 1000$ Hz
  • IMU：$f_i \approx 200\text{—}500$ Hz
  • 相机：$f_c \approx 30$ Hz

正确做法是给每个采样打上 硬件时间戳，在状态估计时按时间戳插值对齐，而不是简单地取「最近一次读数」。

简单取最近值的误差量级：若关节延迟 1 ms、机器人关节角速度 5 rad/s，则角度误差 0.005 rad ≈ 0.29°。听起来不大，但在双足平衡的临界状态下，这个量级的误差足以让控制器做出错误的支撑腿判断。

安装

git clone https://github.com/huggingface/lerobot-humanoid-runtime.git
cd lerobot-humanoid-runtime
pip install -e .

第一步：通电前先扫电机

这一必须在装配完成后、第一次通电时执行，顺序不能颠倒。

# 逐个扫描电机，确认通信与编码器正常
lerobot-humanoid-scan --port /dev/ttyUSB0 --verbose

预期输出应列出所有电机的 ID、固件版本、当前位置与温度。若某个电机无响应，先查接线与终端电阻，不要继续。

第二步：交互式归零

lerobot-humanoid-zero --port /dev/ttyUSB0 --interactive

工具会引导你把每个关节摆到零位并记录当前编码器读数。注意要点：

  • 零位定义在模型资产里（lerobot-humanoid-model 的 MJCF），摆位时要与之一致
  • 使用 关节侧 编码器读数，而非电机侧
  • 归零完成后让机器人保持站立姿态，观察是否对称

第三步：验证关节方向

lerobot-humanoid-verify --check-direction

工具会给每个关节下发一个小幅正指令，并要求确认实际转动方向是否与期望一致。若不一致，在配置里翻转该关节的方向符号——不要改接线，改配置可逆且安全。

第四步：IMU 校准

lerobot-humanoid-imu --calibrate --samples 2000

校准时机器人必须 静止且水平。采集足够多样本以估计零偏；若条件允许，做六面校准可同时估计尺度误差与轴间非正交。

第五步：仿真验证

'''
用统一接口在 MuJoCo 中验证策略
'''
from lerobot_humanoid_runtime import MuJoCoBackend, load_policy

backend = MuJoCoBackend(model_path="assets/humanoid/mjcf/scene.xml")
policy = load_policy("ckpt/walk.onnx", backend="onnx")

state = backend.get_state()
for step in range(1000):
    cmd = policy(state)
    backend.send_command(cmd)
    state = backend.get_state()
    if state.fallen:
        print("跌倒于步", step); break

第六步：上真机

# 先用低增益试运行，确认无异常再逐步提高
lerobot-humanoid-run --policy ckpt/walk.onnx \
    --backend real --port /dev/ttyUSB0 \
    --kp-scale 0.3 --kd-scale 0.5 --max-torque 0.4

务必先用低增益低力矩试运行。这一步的目的是验证接线与方向正确，不是验证性能。确认一切正常后再逐步提高增益与力矩上限。

数据集生成

lerobot-humanoid-record --task walk_forward --episodes 50 \
    --output data/walk_v1 --fps 50

产出的数据集直接兼容 LeRobot 格式，可用 lerobot-train 训练。

该仓库的性能相关要点

Runtime 仓库本身不追求「算法性能」，它追求的是 部署可靠性。但有几个工程指标直接影响最终效果：

指标 影响
控制频率 双足平衡通常要求 ≥ 200 Hz，理想 500—1000 Hz
关节延迟 指令下发到执行的延迟，> 5 ms 会显著恶化平衡
IMU 与编码器对齐误差 系统性姿态误差，影响支撑腿判断
推理延迟 策略前向耗时，需远小于控制周期

双后端推理的取舍

后端 优点 缺点
ONNX Runtime 部署快、依赖少、边缘友好 导出需处理动态轴与算子兼容
PyTorch 调试方便、与训练完全一致 依赖重、启动慢、内存占用高

实践建议：训练与调试用 PyTorch，最终部署用 ONNX，并在切换后做一次数值一致性检查（同一输入下两者输出的最大差异应在 1e-4 量级）。

安全机制的重要性

真机控制器内置的安全机制不是可选项。对双足机器人而言，跌倒时的冲击力矩可以是额定值的数倍。关键保护包括：

  • 位置越限——防止关节转到机械极限
  • 速度越限——防止失控飞车
  • 力矩限幅——这是最后一道防线
  • 通信超时——主机死机时电机应进入阻尼模式，而非保持最后指令继续转

最后一项常被忽略但极其重要：如果通信中断后电机保持最后指令，机器人会以最大力矩持续输出直到断电或损毁。正确行为是 超时进入阻尼/零力矩模式，让机器人软性倒下。

与仿真性能的关系

Runtime 的统一接口设计还带来一个额外收益：可以量化仿真保真度。

方法是在真机上采集一段轨迹（状态序列 + 指令序列），然后在 MuJoCo 中回放相同指令序列，比较仿真轨迹与真机轨迹的偏离。偏离量直接反映仿真模型的动力学误差，可用于指导系统辨识（重新测定质量、惯量、摩擦）。

这是 sim2real 中最实用的一类诊断，而统一接口让它变得成本极低。

与 ROS 2 Control 的关系

两者不冲突，层次不同：

  • ROS 2 Control 解决「如何把控制器接入一个由节点组成的分布式系统」
  • LeRobot Humanoid Runtime 解决「如何把一个训练好的策略跑在这台特定机器人上」

对单机双足而言，Runtime 的路线更轻——没有 DDS 通信开销，控制回路更短，实时性更容易保证。ROS 2 的价值在多机协同与复杂系统集成时才凸显。

与 LeRobot 上层生态的关系

huggingface/lerobot 提供的是 硬件无关的 Robot 类抽象与模型/数据集生态；Runtime 则是 这个本体在抽象之下的具体实现。

关系是：

LeRobot（数据集格式 + 策略实现 + 训练脚本）
        ↓ 调用
LeRobot Humanoid Runtime（本体专用控制器与工具）
        ↓ 驱动
真机电机

这种分层让「换机器人」的成本降到只换 Runtime 层。
