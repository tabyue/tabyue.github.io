多机器人团队的日常

一个典型的小型机器人团队，手里的机器大概长这样：

   机械臂 A        → 厂商 SDK v1.2，Python
   移动底盘 B      → ROS 2 Humble
   桌面臂 C        → LeRobot
   人形 D          → 另一套私有协议

每加一台就要写一套适配，每换一次任务就要改一遍编排脚本。quackd 想做的就是把这一层统一掉。

它的抽象

   ┌──────────────────────────────┐
   │   LLM 大脑（每机一个）        │  决策：做什么
   ├──────────────────────────────┤
   │   VLA / 控制器                │  执行：怎么动
   ├──────────────────────────────┤
   │   本体适配（ROS 2 / SDK）      │  落地：发给谁
   └──────────────────────────────┘

这三层分工是近年 agentic robotics 的主流共识，quackd 的贡献是把它做成了一个 CLI + 一套配置，而不是一套框架让你自己去填。

为什么是 CLI 而不是框架

框架给你抽象，但要你写代码；CLI 给你约定，你写配置。对「先让机器动起来」这个目标，CLI 的前置成本低得多：

  • 不用设计目录结构；
  • 不用选消息队列；
  • 接不上时能很快判断是配置错还是代码错。

代价是深度定制时不如框架灵活。这是一个明确的取舍。

LLM 与 VLA 的分工

层 用什么 频率 职责
决策 LLM 低频（秒级） 任务分解、失败归因、是否换策略
执行 VLA 高频（10—50 Hz） 把「抓起杯子」变成关节轨迹

这个分层与 ros2 模块里讲的运行时分层的道理一致：不要让 LLM 去扛实时性。

  • strands-robots — 另一个用自然语言控制机器人的路线（本期站点已收录 os193）。
  • AgenticRoboRL — 若要让 quackd 里的 LLM 大脑真正变强，后训练是被验证过的路径。
  • ros2 模块「机器人运行时分层」 — 关于为什么 LLM 不该扛实时性的完整讨论。

安装

pip install quackd
# 或从源码
git clone https://github.com/rokbenko/quackd.git && cd quackd && pip install -e .

接入与驱动

# 发现设备
quackd discover

# 接入一台 LeRobot 臂
quackd connect so101 --port /dev/ttyACM0

# 用自然语言下命令
quackd run 'pick up the red block and put it in the box' --robot so101

# 多机协同
quackd run 'arm picks, base delivers' --fleet fleet.yaml

本地模型

quackd run '...' --brain ollama:qwen3 --vla local:smolvla

对不想把场景图像传到云端的团队，本地 LLM + 本地 VLA 这条路径是刚需。

适用边界

适合：原型验证、教学、多机 demo、快速试架构。 不适合：硬实时控制（1 kHz 运控不该走这条链路）、量产部署、有严格安全认证要求的场景。

把它当成把想法跑起来的最快路径，而不是最终的生产运行时。

项目 定位 实时性 适合阶段
quackd 多机统一 CLI + LLM 编排 非硬实时 原型 / 教学 / demo
robonix Rust 写的机器人 Agentic OS 追求硬实时 系统级
horus Rust 写的最快机器人运行时 硬实时 生产运行时
RAI ROS 2 原生具身 AI Agent 框架 取决于 ROS 2 基于 ROS 2 的产品

选型：验证想法用 quackd，要上真机量产再看 robonix / horus / RAI。不要指望一个工具覆盖从原型到量产。
