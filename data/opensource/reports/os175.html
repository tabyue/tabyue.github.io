一个被低估的工程痛点

机器人学习领域的论文越来越多，但复现一个基线往往要花几天：下载 checkpoint、配环境、把评测环境的观测格式转成模型期望的格式、把模型输出的动作转回环境能执行的格式、处理夹爪的开关表示差异……

这些工作没有研究价值，但每一处都可能悄悄出错。更麻烦的是：这些错误不报错，只是让成功率低几个点，而你可能以为是自己的方法不如人。

XPolicyLab 把这层抽出来做成一个共享的适配器层。每个策略只需提供自己的依赖和 checkpoint，观测/动作契约与服务化由框架统一处理。

组合爆炸的算术

假设有 60 个策略和 3 套评测环境。 · 朴素做法：每个策略为每套环境写一份适配 → 180 份代码； · XPolicyLab：每个策略写一份适配器，每套环境写一份适配器 → 63 份。

而且新增第 61 个策略时，朴素做法要补 3 份，XPolicyLab 只需补 1 份。

XPolicyLab 的核心思想：中间定义一层与双方无关的观测/动作契约。
"""
class UnifiedContract:
    observation = dict(rgb=[...], depth=[...], state=[...], instruction=str)
    action      = dict(joints=[...], eef_pose=[...], gripper=float)

def run(policy_name, env_name, task):
    policy = registry.load(policy_name)      # 只关心自己的依赖与权重
    env    = registry.load_env(env_name)
    while not task.done():
        obs_u = env.adapter.to_unified(env.observe())
        act_u = policy.adapter.predict(obs_u)
        env.step(env.adapter.from_unified(act_u))

上手顺序建议：

  1. 先跑通一个已有策略 + 一个已有环境，确认适配器链路正常；
  2. 再接入自己的策略——只需实现 adapter.py 的to_unified / from_unified 两个方向；
  3. 最后在真机上用标准化评测验证。
