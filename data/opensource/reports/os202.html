灵巧操作仿真的三个痛点

做过多指灵巧手仿真的人基本都踩过下面三个坑：

其一，接触求解慢。 手内操作每帧可能有几十个接触点同时激活，通用引擎的求解器在这种密度下要么发散、要么步长得调到很小，仿真吞吐直接掉一个数量级。

其二，任务搭建碎。 要让一只 20+ DoF 的手完成「把笔转过来再握住」，你得自己写 URDF/USD、调初始姿态、设接触参数、写奖励。这些工作分散在不同工具里，没有一条贯通的链路。

其三，RL 接口各写各的。 并行环境怎么开、观测怎么打包、动作怎么归一化——每个团队一套。换一个引擎就得重写。

SuperDex 的做法是把这三层一起开源：物理引擎、创作工具、RL 接口是同一个平台的一部分，而不是让用户自己拼。

为什么要自研物理引擎

通用物理引擎的设计目标是「什么都能仿」：刚体、软体、流体、绳索。但灵巧操作需要的恰恰相反——在极窄的场景里做到极稳极快。

这个取舍可以写成一个三角：

        通用性
          /\
         /  \
        /    \
   稳定性 ——— 速度

通用引擎在「通用性」这一角上投入了大量复杂度，代价是接触密集场景下稳定性与速度难以兼得。专用引擎放弃通用性，把预算全部押在剩下两角。

      创作工具（authoring）
            │  产出任务定义 / 机器人资产
            ▼
      物理引擎（simulation core）
            │  产出状态转移与观测
            ▼

            │  并行环境 / 观测打包 / 动作归一化

关键点在于：三层共享同一套资产与状态表示。创作工具写出的手，就是物理引擎里跑的那只手，也是 RL 接口暴露给算法的那只手——中间不存在格式转换导致的语义漂移。

与现有生态的关系

  • MuJoCo / MJX：通用引擎，接触丰富场景需大量调参，MJX 提供 GPU 并行；
  • Isaac Lab：建立在 PhysX 之上，生态完整，但物理层不可替换；
  • Genesis：统一平台形态，同样追求通用物理仿真；
  • SuperDex：物理层自研，聚焦接触密集的灵巧操作。

典型使用路径

1. 用创作工具定义/导入机器人资产（灵巧手、机械臂）
2. 搭建任务：初始姿态、目标、接触参数
3. 通过 RL 接口开并行环境
4. 接入训练循环（PPO / SAC 等）
5. 评估 sim-to-real 迁移

建议的最小验证

在投入大规模训练之前，先做一个接触稳定性探针：

- 让手指以固定力压向一个刚性平面
- 逐步增大接触点数（1 / 8 / 32 / 64）
- 记录：是否穿模、单步耗时、能量漂移

这三项一旦在某个接触密度上崩掉，后面所有 RL 结果都不可信。

适用边界

适合：

  • 灵巧手 / 多指操作的仿真与 RL；
  • 接触密集、通用引擎难以稳定的场景；
  • 需要从资产到训练一条链路贯通的团队。

不适合：

  • 需要流体、软体、绳索等非刚体模拟的任务；
  • 已有成熟 Isaac Lab / MuJoCo 管线且没有接触稳定性问题的项目；
  • 需要长期 API 稳定性的生产环境（项目仍在快速演进）。

选择时的第一性问题应该是：我的任务里接触点密度有多高。密度低（如抓取一个方块）时各家差别不大；密度高（手内重定向、多指协同）时，物理层的差异会被指数级放大。
