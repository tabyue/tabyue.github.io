为什么值得关注：Code-as-Policy 的卖点是让大模型输出可检查、可执行的程序，而不是不可解释的动作向量；但真正落地时最缺的往往不是模型，而是 Harness、训练配方与基准适配这些工程脏活。把这些固化成仓库，等于把「能演示」推到「能复现、能改」。

  1. CaPtain-Harness：机器人 Agent 的运行壳，负责把任务、观测、可用 API 与评测协议打包成统一接口；
  2. SFT 阶段：用示范轨迹（任务描述 → 程序 / 动作序列）做监督微调，建立基础的程序化策略；
  3. RL 阶段：在环境反馈上继续改进策略，把成功率或任务奖励回传到模型；
  4. Benchmark adapters：把不同机器人基准的观测格式、动作空间与成功判据适配到同一套训练循环；
  5. 评测闭环：Harness 既用于训练采样也用于评测，避免训练与评测口径不一致。

分层的要点是：训练代码不直接绑定某个基准，适配层承担格式差异；这样换基准时只需替换 adapter，而不是重写训练循环。

  • Code as Policies（Liang et al., 2023）：把语言模型生成的程序作为机器人策略，是这条路线的方法起点；
  • 本站 p328（VLA-Tug）：运行时失败监测与失败模式分类，可作为 Code-as-Policy Harness 的兜底层；
  • 本站 p331（Latent RL Priors）：仿真 RL 控制知识蒸馏到视觉策略，与「SFT → RL」两阶段结构可对照阅读；
  • 本站具身 Agent / Harness 相关章节：解释 Harness 为什么是 Agent 系统的第一等组件。
  1. 克隆仓库并按 README 安装 Python 依赖（建议独立虚拟环境）；
  2. 先跑通 CaPtain-Harness 的一个最小环境，确认观测、动作与成功判据的口径；
  3. 用自带示范数据跑一遍 SFT，确认模型能产出可执行的程序化策略；
  4. 再开启 RL 阶段，注意采样吞吐与奖励尺度，先在小任务上验证收敛；
  5. 通过 benchmark adapters 接入目标基准，与基线做同口径对比。

仓库公开的是流水线与训练配方，不是一份刷榜成绩单。评价它更应看三件事：同一基准上 SFT 与 SFT+RL 的差距是否可复现、换 adapter 后训练循环是否无需改动、以及 Harness 的评测口径是否与训练一致。这三点决定了它能不能作为后续实验的地基。
