strands-robots 的出发点是：大模型 Agent 已经会规划、会调工具、会记住上下文，但它还不会拧螺丝。

两层能力的缺口

   Agent 层（已成熟）              策略层（已成熟）
   任务分解 / 工具调用   ─── ✕ ───   VLA / WAM 出动作
   记忆 / 多轮对话                   仿真训练 / 真机部署
        │                                    │
        └──────────── 缺一层 ────────────────┘

过去两年，两侧各自进步很快，但中间怎么接一直靠各团队自己写胶水代码：Agent 输出一段文字 → 手写解析 → 调策略 → 拿回结果 → 再转成文字喂回 Agent。

strands-robots 的做法是把机器人能力做成 Agent 的原生工具，让「抓起来」「放到左边」「看看有没有红色物体」这些能力像调用 API 一样被 Agent 使用。

这个分层的价值

为什么不端到端？ 因为两层的迭代节奏与失败模式完全不同：

Agent 层 策略层
迭代周期 天—周（改 prompt / 加工具） 周—月（采数据 / 重训）
失败模式 规划错、理解错 动作不精、泛化差
评测方式 任务完成率、轮次 成功率、轨迹质量
出错代价 低（可重试） 高（可能损坏物体）

分层后，Agent 层的错误可以在 Agent 层修（改 prompt、换工具），不必重训模型。这对真实业务落地是决定性的——毕竟没人愿意因为「任务分解逻辑改了」就重训一次 VLA。

  • 想让机器人能力被上层业务系统（工单、ERP、对话系统）调用的团队；

关键设计决策

1. 机器人能力即工具（robot-as-a-tool）。 每个机器人能力被封装成一个有明确输入输出 schema 的工具。Agent 不需要知道底层是 VLA 还是 WAM，只需要知道「调用 grasp(target) 会返回一个成功标志与观测」。

2. 观测结果回流到 Agent 上下文。 这是「闭环」的关键：工具执行后的观测（成功了吗？桌上还剩什么？）必须回到 Agent 的上下文，否则 Agent 无法做下一步决策，也无法从失败中恢复。

3. 世界基础模型作为「想象」工具。 这是比较前瞻的一点：把 WAM 封装成 predict() 类工具，让 Agent 在实际执行前先在想象里试一次，筛掉明显会失败的动作。这比让 Agent 盲试安全得多。

4. 复用 Strands Agents 生态。 不自建 Agent 框架，直接复用成熟的工具调用、规划与记忆能力——这让机器人能力可以立刻与非机器人工具（查数据库、发消息、调 API）混编在同一个任务流里。

建议的上手顺序

Step 1：先不接真机，用 mock 工具跑通 Agent 循环。

# 伪代码：先验证 Agent 能否正确编排，不碰硬件
from strands import Agent
from robots import RobotTools

tools = RobotTools(backend='mock')      # mock 后端，不连硬件
agent = Agent(tools=tools)
result = agent("把桌上的蓝色零件放到左边的料盒里")
print(result.tool_calls)   # 看它调用了哪些工具、顺序是否合理

Step 2：逐个替换成真实能力。 一次只换一个工具（先换 observe，再换 grasp），每次都验证 Agent 的编排是否仍然合理。不要一次全换，否则出错时无法归因。

Step 3：加上失败恢复。 这是 Agent 层相对端到端方案最大的优势，务必用起来：

@tools.on_failure
def recover(error, context, agent):
    return agent(f"执行 {context.tool} 失败：{error}。请分析原因并尝试替代方案。")

三条实操建议

  • 工具 schema 要写清楚物理约束：grasp 的输入不只是物体名，还应包括期望姿态、力度上限。schema 越明确，Agent 越少产生不可执行的调用；
  • 观测必须结构化回传：不要让 Agent 自己去看图像，把「有什么物体、在哪、抓取是否成功」做成结构化字段；
  • 保留人工确认闸门：涉及不可逆动作（丢弃物体、施加大力、移动到人附近）时强制人工确认。

定位性收益

  • 把 Agent 生态与机器人能力接上：让规划、记忆、工具编排这些成熟能力可以直接服务物理设备；
  • 分层带来迭代效率：Agent 层的错误改 prompt 即可，不必重训模型；
  • 天然支持长程任务：Agent 擅长多步编排，正好补上 VLA 在长程任务上的短板；
  • 世界模型可作为「想象」工具：执行前先试一次，降低试错成本与硬件风险；
  • Apache-2.0 + 活跃维护：商用友好，2026-02 至今持续推送。

需要注意的限制

  • 依赖 Strands Agents 生态：若不打算用 Strands，接入成本会上升；
  • 分层带来延迟：每层调用都有开销，高频率闭环控制不适合走这条链路（应由底层策略直接闭环）；
  • Agent 的不可预测性：自然语言 Agent 可能生成未预期的工具调用序列，必须有安全闸门与动作白名单；
  • 真机能力依赖底层模型：框架不提供 VLA/WAM 本身，只提供接入方式，实际能力取决于你接的模型。

一句话选择：要长程任务与业务系统集成 → strands-robots；要 ROS 2 生态内的 Agent 化 → RAI；要高频精密操作 → 端到端 VLA。

实践中的组合：strands-robots 负责「做什么、按什么顺序做」，VLA 负责「这一步具体怎么动」，底层控制器负责「电机怎么转」。三层各司其职，是 2026 年具身系统的主流形态。
