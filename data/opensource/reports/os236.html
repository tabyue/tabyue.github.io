RUA（Robot-Use Agent）把大模型当规划器，每一步感知、推理、重试都要走一遍模型调用。上下文越堆越长，成本与延迟同步上升，而长上下文本身还会稀释关键观测——这是很多「Agent 越跑越笨」的根因。

PyRUA-Lean 来自北京大学 DAGroup，主题非常明确：Fewer Tokens, Better Action —— 在 GPT-6 Astra 一类前沿模型驱动的机器人智能体上，用 14% 更高的成功率换取 65% 更少的 token 消耗。它研究的不是怎么把模型变强，而是上下文与调用预算的治理：哪些历史该留、哪些工具结果该压缩、什么时候该直接出动作而不是再想一轮。

按 token 预算治理类工作的常见结构，可大致分为三块：

  1. 上下文构造与裁剪：决定每轮送进模型的观测帧数、历史步数、工具描述详略。
  2. 工具结果压缩：把长执行日志、失败轨迹压成结构化摘要，而不是原文堆积。
  3. 决策门控：判断当前是否已有足够信息直接输出动作，避免无意义的额外推理轮次。

这三块正好对应一次调用成本的分解：输入 token 由前两块决定，调用轮数由第三块决定。PyRUA-Lean 的收益同时来自两者，这也是「更少 token 反而更高成功率」并不矛盾的原因——砍掉的是噪声，不是信息。

注意：以上分层是按项目定位归纳的工程解读，具体实现以仓库为准。

  • PyRUA-Lean 仓库 — 官方实现与配置。
  • Democratizing Robot-Use Agents（arXiv 2611.01560） — 统一 RUA Harness，理解组件边界的前置阅读。
  • TinyAstral（arXiv 2610.41216） — 靠蒸馏降低推理成本的互补路线。
  1. 先测自己的基线预算：在自有任务上统计每 episode 的输入 token、输出 token 与调用轮数，没有基线就无法判断裁剪是否划算。
  2. 一次只改一个裁剪维度：先改历史帧数，再改工具结果压缩，最后动决策门控。多个维度同时改，成功率掉了无法归因。
  3. 把成功率与 token 一起报：只报省了多少 token 没有意义，必须证明任务成功率没有下降（本项目还做到了上升）。
  4. 做配对评测：裁剪前后在完全相同的 episode 上对比，否则任务难度差异会淹没收益。
  5. 再和开源 Harness 组合：可与 uni-robot-agent（p307）的模块化接口、TinyAstral（p308）的蒸馏流程叠加，做 token 层面的对照实验。

项目自身的口径：

指标 变化
任务成功率 +14%
token 消耗 -65%

怎么读这两个数字，成功率提升与 token 下降同时出现，最可能的机制是上下文噪声被削减后，模型对当前观测的注意力更集中、格式遵循更稳定。这与 uni-robot-agent 强调的「四项通用能力应联合培养」是同一方向的不同切入点。

评估自己场景时建议补三类指标：单 episode 端到端延迟（不只是 token）、失败后的重试轮数、以及长程任务（>20 步）上的收益衰减。短任务省下的 token 未必能外推到长程。

注意：结论绑定特定 planner 与任务集，换模型或换基准后收益幅度需重新测；把它当成「预算治理」的方法参考，而不是可以直接抄的固定配置。

对比 uni-robot-agent（p307）：后者提供统一、可插拔的 Harness 基座，解决「能不能研究与消融」；PyRUA-Lean 专注其中上下文与预算这一个维度，解决「跑得起、跑得久」。二者可叠加。

对比 TinyAstral（p308）：TinyAstral 靠蒸馏把能力压进 4B 小模型来降低推理成本，是换模型的路线；PyRUA-Lean 不改模型，只改送进去的上下文，是改输入的路线。两者正交互补。

对比简单截断历史：粗暴截断能省 token 但常掉成功率，因为丢了失败诊断与恢复线索。PyRUA-Lean 的价值在于有选择地保留信息，这也是「更少 token 反而更好」的关键区别。
