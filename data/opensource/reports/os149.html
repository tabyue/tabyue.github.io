它想解决什么问题

长时程家务任务（「把咖啡袋放到岛台上，再把用完的纸盒扔掉」）对人形机器人的要求，和实验室里的取放任务完全不同：

  1. 任务不是一次性的——要连续做对好几件事；
  2. 环境不完全已知——得先看看厨房里有什么、东西在哪；
  3. 需要记住——第二次来的时候应该知道垃圾桶在哪个角落。

HomeBody 的定位就是这样一个会自己探索、记住场景并动手干活的智能体，而不是执行预编排脚本的执行器。

SIM 阶段已经能玩什么

在 MuJoCo 里的一个 real2sim 厨房场景中，驱动 Unitree G1 一次一个技能地完成任务：

  • 决策依据：机器人的相机画面 + 场景地图 + 对场景的记忆；
  • 物理完整性：行走策略、手臂、Dex3 灵巧手与每一个物体都用完整物理模拟；
  • 场景来源：复现了 SRC Kitchen 中的长时程任务，即真实厨房被数字化后放进仿真。

交互方式

启动后打开 http://127.0.0.1:8080，输入任务并点「Start task」即可。也可以用无头模式跑单条任务，或用脚本化序列做管线自检（不需要模型）。

为什么值得关注

具身智能体（embodied agent）方向的开源代码长期稀缺：多数仓库要么只放模型权重，要么只放单一技能的策略。HomeBody 放的是完整的智能体闭环——感知、记忆、决策、执行、评估、回放，而且提供了可复现的仿真环境。对想研究「长时程 + 记忆」的团队，这是一个可以直接开工的底座。

记忆层为什么是核心

长时程任务的失败往往不是单个动作做错，而是做到一半忘了前面。具体表现为：

  • 已经确认过垃圾桶位置，第二轮又重新找一遍；
  • 物体被移动后，模型仍按旧位置规划；
  • 任务后半段忘了最初的目标状态。

HomeBody 把「对场景的记忆」显式列为决策输入之一，就是为了处理这类问题。这与 ROMA 的感知链、以及 VLA 长时程记忆方向的工作是同一个问题的不同侧面。

决策核心可替换的设计

仓库支持多家模型（Astra / Opus / 以及通过 API key 接入的 -api 系列）。这个设计有两层好处：

  1. 不被单一模型绑定：可以对比不同模型在同一仿真任务上的规划质量；
  2. 可以跑无模型基线：tools/check_manipulation.py 提供脚本化序列，用来验证仿真与执行管线本身没问题——这在调试时极其有用，能把「模型决策错误」和「执行管线错误」区分开。

评估与回放工具链

工具 作用

tools/score_session.py 判断每个物体是否最终归位

理解这个系统的背景读物

长时程与记忆方向

  • MemoryVLA（shihao1895/MemoryVLA）——把记忆机制显式引入 VLA，与 HomeBody 的场景记忆是同一问题的不同实现层。
  • EvoMem-VLA（站内论文）——状态演化记忆用于长时程任务。
  • Long-WAM（站内论文）——延长视觉上下文到 19 秒，叠杯成功率从 63.3% 提升到 78.7%，说明上下文长度本身就是长时程能力的一种实现方式。

分层智能体方向

  • Harness VLA（清华 × 正行创新 × 无问芯穹）——把冻结的 VLA 封装为 VLA_ACT primitive，由 Agentic Planner 组织解析式 primitive 与它，是「大模型组织专家模型」的代表。
  • RPent（RLinf/RPent，清华 × 无问芯穹）——具身智能体基础设施，端到端任务加速 7 倍。
  • SuperNav——保持预训练 MLLM 的通用性，把运动交给导航技能与物理交互工具，已在真实四足上部署。

建议的阅读路径

  2. 读 MemoryVLA 或 Long-WAM，理解「记忆 / 长上下文」在 VLA 层怎么做；

安装

# 1. 取代码并建立 Python 3.11+ 环境
git clone https://github.com/Stanford-TML/homebody
cd homebody
python -m venv .venv && source .venv/bin/activate

# 2. 安装（-e 不能省，资产文件从当前目录读取）
pip install -e .

# 3. 接一个模型（三选一）
npm install -g @openai/codex && codex login      # --model astra
npm install -g @anthropic-ai/claude-code && claude   # --model opus
export OPENAI_API_KEY=...                        # 或 ANTHROPIC_API_KEY

# 4. 自检（check 不启动任何进程；provider-check 会发一个短请求）
homebody check
homebody provider-check --model astra

无 GPU 或 Mac 用户：GPU 是可选的。缺 CUDA 时行走策略自动跑 CPU；渲染后端会自动选择（Linux 有 GPU 用 egl、无 GPU 用 osmesa、macOS 用 cgl）。Linux 无 GPU 需额外：

sudo apt install libosmesa6
pip install torch --index-url https://download.pytorch.org/whl/cpu

跑一个任务

# 交互式：打开 http://127.0.0.1:8080，输入任务后点 Start task
homebody --env src_kitchen --model astra

# 无头模式跑单条任务
homebody --headless --env src_kitchen --model opus \
  --task "Put the coffee bags on the island and throw away the used cartons."

# 无模型的脚本化序列（用于验证执行管线，四个物体一次移动）
python tools/check_manipulation.py --sequence configs/continuous_four.json --no-visuals

控制台默认无登录，除非网络可信，否则保持 --host 在 localhost。

跑完之后看什么

run=$(ls -d runs/session-* | tail -1)      # 最新一次运行
python tools/timeline.py $run              # 逐步决策与结果
python tools/score_session.py $run         # 物体是否都归位
python tools/compose_cockpit.py $run       # 生成回放视频 cockpit.mp4

建议的上手顺序

  1. 先跑 check_manipulation.py，确认仿真与执行管线正常（不依赖模型）；
  2. 再用 --model astra 跑一个短任务，观察 timeline；
  3. 最后挑战多物体长时程任务，用 score_session 逐物体打分。

跳过第 1 步直接上模型是常见的调试陷阱——分不清是模型错了还是管线错了。

  • 任务总数与成功率分布；
  • 与基线方法的横向对比；
  • 多次运行的方差。

因此不应把它们当作性能指标引用。真实的能力边界要等 REAL2SIM（10/12）与 REAL（10/19）阶段放出后，才有真机数据可谈。

应该自己测什么

如果要把它当作研究底座，建议自建一套可复现的度量：

指标 定义 为什么重要
技能成功率 单个技能（导航/抓取/放置）的成功比例 定位是执行问题还是规划问题
任务完成率 完整任务达成比例 端到端能力
首次尝试后的重规划次数 一次任务中重新规划的次数 反映记忆与状态跟踪质量
重复探索率 已探索区域被再次探索的比例 直接度量记忆是否有效

后两项是长时程智能体的关键指标，也是 HomeBody 声称要解决的核心问题——值得自己动手量化，而不是等官方数字。

算力需求

  • 有 GPU：正常路径；
  • 无 GPU / Mac：行走策略可跑 CPU，但吞吐显著下降，长时程任务的墙钟时间会很长。

做批量实验建议至少准备一张消费级 GPU；只做管线验证则 CPU 足够。

与同类开源项目的位置差异

项目 定位 与 HomeBody 的关系
openpi（Physical Intelligence） VLA 策略与权重 提供「单个技能怎么做」，不解决「先做哪个」
lerobot（HuggingFace） 机器人学习数据集与策略库 偏数据与模型层，缺少智能体闭环
Isaac Lab-Arena（NVIDIA） 可组合的大规模仿真评测 偏评测基础设施，偏并行吞吐
HomeBody 人形智能体闭环（探索 + 记忆 + 长时程决策） 关注规划与记忆，可复用上述项目的技能层

一句话概括：别人做的是「技能」，HomeBody 做的是「把技能组织起来完成一件长事」。

与 VLA 路线的关系

互补而非竞争。VLA 解决「看到这个画面、听到这个指令，手该怎么动」；HomeBody 解决「厨房里有五件事要做，先做哪件、做完记什么、下一步去哪」。

一个合理的组合方式是：用 VLA 作为 HomeBody 技能层的实现（抓取、放置），用 HomeBody 的决策与记忆层做上层组织。这与 Harness VLA、RPent 等「大模型 + VLA 分层」的思路一致——通用模型负责理解与规划，专家模型负责高精度执行。

与 real2sim 路线的关系

HomeBody 的仿真场景是 real2sim 厨房：真实厨房被数字化后放进 MuJoCo，用于复现 SRC Kitchen 的长时程任务。

这条路线与纯合成场景（随机摆放的物体）相比，优势在于任务分布真实——物体的种类、摆放方式、空间关系都来自真实厨房。代价是场景固定，泛化到新环境需要重新做一次重建，这正是 REAL2SIM 阶段要提供的能力（探索与场景重建管线）。

选择建议

  • 想研究长时程规划与记忆 → HomeBody 是合适的起点；
  • 想研究单个操作技能的精度 → 应看 openpi / lerobot / dexbotic；
  • 想做大规模并行评测 → Isaac Lab-Arena 更合适；
  • 想搭生产级数据管线 → AWS Physical AI Toolchain 更对口。
