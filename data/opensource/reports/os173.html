从 Computer Use 到 Robot Use

大模型智能体已经能编写程序、操作电脑、调用工具完成复杂数字任务。CodeActionBench 问的是：把工具换成机器人，同样的能力还剩多少？

它与同期 RobotWorld 的差别在于聚焦度：RobotWorld 铺开 84 项任务、8 类本体做广度扫描；CodeActionBench 只用双臂操作这一个设定，但把评测协议做深——25 个任务 × 9 个配置 × 多次尝试，看的是同一批任务上不同模型与框架配置的能力剖面。

为什么要「共享接口」

这是整个评测设计的枢纽。接口给多少帮助，就决定了评测测的是什么：

接口提供 评测测的是
物体位姿 + 抓取候选 「会不会调用现成模块」
完整技能库 「会不会编排技能」
只有图像 + 机器人状态 「能不能从观察里构造动作目标」

CodeActionBench 选第三种。它不额外做任务专属微调，也不提供任务示范、专门的感知或抓取模块输出、特权场景状态、预设任务策略。

评测检查三件事，不只是成功率

  1. 任务结果：最终是否完成
  2. 中间进展：走到哪一步（部分完成也有信息量）
  3. 完成判断：模型自己认为做完了没有

第三项常被忽略但极关键——判断失败并继续尝试是自主性的核心。一个总是误以为自己成功的 Agent，在工业场景里比一个明确知道自己失败的 Agent 危险得多。

评测流程

"""
CodeActionBench 风格的评测循环：Agent 自行选择视觉证据、写代码、看反馈再改。
"""
def evaluate(agent, task, budget=30):
    obs = task.get_observation()          # 仅图像 + 机器人状态
    workspace = CodeWorkspace()

    for step in range(budget):
        patch = agent.generate(obs, task.instruction, workspace.history)
        workspace.apply(patch)
        action = workspace.next_action()
        obs, done = task.step(action)

        if workspace.claims_done():       # 完成判断也被评测
            return Result(verified=task.check_success(), steps=step + 1,
                          progress=task.progress())
    return Result(verified=False, steps=budget, progress=task.progress())

维度 含义 为什么重要
任务结果 成功条件是否满足 主指标
中间进展 部分完成的程度 区分「完全不会」与「差一步」
完成判断 Agent 自报是否与实际一致 自主性的核心能力

前置依赖

RoboTwin 2.0 与 SAPIEN 的环境配置是主要工作量，建议先单独跑通这两个依赖的官方示例，再接入本基准。

最小验证流程

  1. 先在单个任务上跑通闭环：确认 Agent 能拿到图像、能提交代码、能收到反馈。这一步通了剩下的都是调参
  2. 固定预算再对比不同配置：预算（步数上限）必须一致，否则成功率不可比。论文用统一的 675 次尝试分摊到 9 个配置
  3. 一定要记录「完成判断」：Agent 自报完成 vs 实际成功的混淆矩阵，是这份基准最有价值的产出
  4. 别急着上真机：先在仿真里把「视觉证据选择」这一环跑明白——多数失败发生在这里而非动作生成
  5. 做框架配置对照：同一个模型在不同 harness 下差异巨大（Opus 5 在 Reference harness 与 Claude Code 下是 49.3% vs 45.3%），说明 harness 本身就值得优化

排错要点

  • 成功率普遍偏低：检查是否误给了特权状态（会让结果虚高）或误屏蔽了反馈（会让结果虚低）
  • 中间进展高但最终成功率低：典型的「会做但收不了尾」，多半是完成判断逻辑有问题
  • 不同配置差异过大：可能是预算或重试次数设置不一致，先对齐评测协议
  • 仿真与论文数字不符：确认 RoboTwin 2.0 与 SAPIEN 的版本，物理参数变化会显著影响结果

主结果（尝试成功率）

配置 成功率
GPT-6 Astra（Codex CLI） 73.3%
Claude Opus 5（Reference harness） 49.3%
Claude Opus 5（Claude Code） 45.3%
全部 9 个配置的最低值 2.7%

规模：25 个双臂仿真任务，9 个模型与运行框架配置，共 675 次尝试。

三个值得注意的读数

  1. 2.7% 到 73.3% 的跨度说明「框架配置」和「模型能力」同等重要。 同一个模型换 harness 能差 4 个百分点（Opus 5：49.3% vs 45.3%），不同模型在同一 harness 下能差 20 个百分点以上。
  2. 73.3% 是「尝试成功率」不是「任务成功率」。 它衡量的是在给定预算内尝试后完成的比例，读这个数字时要连同预算一起看。
  3. 中间进展维度比最终成功率更能定位问题。 一个配置可能最终成功率低但进展高，说明它「会做但收不了尾」；另一个可能都低，说明「根本不会」。这两种失败需要完全不同的修复手段。

读表要点：这些基准不互斥，测的是不同切面。如果你要回答「哪个通用模型最适合做机器人 Agent」，用 RobotWorld 或 CodeActionBench；如果要回答「我的 VLA 泛化好不好」，用 BiDex-100 或 RoboDojo。特别提醒：CodeActionBench 的接口帮助最少，因此它的绝对成功率数字不能与支持特权状态的基准直接比较。

与 EmbodiedEvo 的关系：两者都关注「代码即策略」，但角色不同——CodeActionBench 是尺子（评测），EmbodiedEvo 是选手（方法）。用 CodeActionBench 的协议去测 EmbodiedEvo 是很自然的下一步。
