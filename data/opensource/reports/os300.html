General-Sequences/sequence-ai 于 2026-11-17 建立、11-18 仍有推送，Apache-2.0 许可，约 21 star，主语言 Python，项目主页 generalsequences.com。它解决的问题很具体：机器人本体上的算力、功耗与散热预算有限，而 VLA / WAM 策略越来越吃 GPU；能不能把策略推理搬到远端 GPU，让本体只跑一个轻量客户端？

仓库 README 把框架明确分成三层——推理层（CUDA Graphs 保证同一输出、在每个机器人的 slack 内 batching、多副本）、网络层（机器人与其 GPU 之间的连接）、以及托管 GPU 的客户端。topics 里同时出现 gr00t、openpi、lerobot、action-chunking、remote-inference、scheduling，说明它面向的是主流开源策略栈而非自研模型。

为什么值得看：「云端推理」这个说法在具身领域常被一句带过，真正难的是控制周期。动作块（action chunk）给本体留了一段等待窗口，远程推理必须在这段 slack 内完成取图、传输、推理与回传；sequence-ai 把这个约束写进了 batching 策略本身，这是它与通用模型服务框架最本质的区别。

  1. 本体侧客户端：采集观测、序列化请求、接收动作块并交给控制器；本体不持有模型权重。
  2. 网络层：维护机器人到指定 GPU 的连接，处理广域网下的抖动与重连；连接与 GPU 绑定，而不是无状态轮询。
  3. 推理层（核心）：用 CUDA Graphs 把一次策略前向固化成可复用计算图，减少 kernel 启动开销并保证输出一致；多个机器人的请求在每个机器人各自的动作块 slack 内做 batching，既提高 GPU 利用率又不越过控制周期；多副本承载不同机器人或不同策略。
  4. 调度约束：slack 是硬预算——batching 窗口不能超过任一参与机器人剩余的动作块执行时间，否则远程推理带来的吞吐优势会被延迟反噬。

  • VSpark: Speculative Decoding for Autoregressive VLA（arXiv 2611.22666，本轮 p387）：在解码步数上省预算，与远程服务的网络预算可叠乘。
  • Task Convergent Flow Matching for Generative Robotics（arXiv 2611.22609，本轮 p391）：推理时并行物理 rollout 验收候选，是另一种推理算力花法。
  • SR-VLA: Stall-Reduced VLA Execution via Predicted-Input Lookahead and Selective KV Cache Repair（arXiv 2611.22356）：直接处理推理阻塞导致的控制停顿，与 slack 约束是同一问题。
  • GR00T / openpi / LeRobot：仓库 topics 明确对接的主流开源策略栈，接口与动作分块格式以各自文档为准。

  1. 先在本地回环跑通：把客户端与 GPU 放在同一台机器上，确认动作块输出与本地直接推理一致（CUDA Graphs 的输出一致性声明要实测），再引入网络。
  2. 量出你的 slack：记录控制器执行一个动作块的时长，这就是 batching 窗口的上界；不要直接用 README 的默认窗口。
  3. 压测分三段：客户端序列化、网络往返、GPU 推理分别打点，找出瓶颈在哪一段——这与站内 /learn/ai-infra 深化的可观测性里「延迟要拆开埋点」是同一条原则。

  5. 断连降级必须设计：远端不可达时本体应有安全动作（保持、急停或本地小策略），不能让控制回路空转。
