为什么自改进必须被系统化

本轮多条工作（Harness VLA、RAX、EMHO）指向同一结论：模型能力的释放取决于它外面那层 harness。但 harness 目前基本靠人手写，改一次要一轮工程迭代。如果 harness 可以被 Agent 自己评估和修改，迭代周期就从「人天」降到「小时」。

适用与不适用

适合：已经有稳定的模型与工具接口、想加速系统层迭代的团队；需要把「经验 → 系统改动」这条链路自动化的场景。 不适合：连基础工具链都还不稳的早期项目——自改进的前提是有一个可评估的基线，基线不收敛时自我修改只会放大噪声。

关键设计：改动要可回滚

自改进系统的可靠与否，取决于能不能安全地拒绝一次坏改动。因此 harness 必须版本化，每次改动都要在留出任务集上回归验证，收益为正才合并，为负则回滚。这与软件开发里的 CI 是同一个道理，只是被改的对象从代码变成了提示与编排逻辑。

与 EmbodiedEvo / ASPIRE 的差别

ASPIRE 与 EmbodiedEvo 演化的对象是技能库，PhyAgentOS 演化的对象是整套 harness——包括进度判断、感知工具调度、视觉 grounding 的落实方式。范围更大，风险也更高，因此更需要严格的回归验证机制。

  • Harness VLA — 把 VLA 收缩为 VLA_ACT 原语、由 Agentic Planner 组织的系统层思路，与 PhyAgentOS 的 harness 抽象同源。
  • RAX: Scaling Online Exploration for Robot Agents — 让机器人智能体把在线探索固化为可复用程序，是「经验 → 系统资产」的实例。
  • EMHO: Embodied Agent Harness Optimization via Experience Traces — 把整套 harness 当优化对象，并给出多子任务共享时的增益—损失感知合并策略。
  • ASPIRE — NVIDIA GEAR Lab 的持续技能发现，演化对象是技能库而非 harness。

建议的上手顺序

  1. 先跑一个固定 harness 的最小任务，建立成功率基线。没有基线的自改进无法判断收益。
  2. 准备留出任务集：与训练/调试任务同分布但不重合，用于回归验证。
  3. 开启自改进闭环，但先只放开提示词级别的改动，观察改动是否可解释。
  4. 逐步放开编排与工具调度级别的改动，每一步都记录收益/损失。
  5. 把每次改动沉淀成 diff，人工审一遍——自改进不等于无人审。

落地提醒

具身场景的反馈信号稀疏且诊断性弱（常只有「动作合法/非法」与回合末的 0/1），因此归因是自改进的最大难点：一个回合几十步，很难定位是哪一步导致的失败。上线前应先把轨迹日志与中间态观测做扎实，否则自改进只能盲改。

需要自行验证的点

  • 自改进在稀疏反馈下的归因能力；
  • 多子任务共享一个 harness 时的改动冲突（这正是 EMHO 提出的 EMHO-Merge 要解决的问题）；
  • 长期运行中的灾难性遗忘风险——改来改去可能把早期有效的行为覆盖掉。

与同类项目的对照维度

评估这类系统时，建议只看三个指标：留出任务集上的成功率增量、单个改动的平均验证成本、回滚率。回滚率过高说明归因不准，验证成本过高说明不适合高频迭代。
